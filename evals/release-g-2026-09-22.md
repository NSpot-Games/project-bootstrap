## The 57 improvisations

The count rose again with grain: this run reported every small judgement, fifty-seven lines in
the final list against forty-five. They triage into six procedure gaps covering fourteen of
them, thirty-nine clarifications and four that are not gaps. None of the six is one release G
closed, and all six sit in the design-doc sessions or at generation, where the run made more
decisions of its own than any earlier run, because the three contradictions and a richer
history gave it more to reconcile.

1. **The bootstrap's own choices.** §3(a) says how to record a recommendation the user
   delegated; it says nothing about a choice the agent makes alone while writing a doc (an
   invented URL, a latency budget, a queue due date, a retention period). The run marked each
   *recommended, not confirmed* and gave a row only to the expensive ones, which is right and
   should be the rule.
2. **A delegated contradiction.** "Take your recommendation" on a contradiction the procedure
   says the user decides: is the result the owner's decision or a recommendation? The run read
   it as the owner's. §6a step 3 should say so, and say that contradictions decided before the
   open-questions file exists need no row.
3. **Editing a doc that has passed its gate.** Changelog lines, a schema extension, a swap of
   two build steps, a renumbered step inside an owner decision: none was re-gated. §3(b) should
   say an edit that changes a decision is flagged in the next gate message, and anything else
   needs only its changelog line; and that a contradiction the bootstrap finds between two of
   its own reviewed docs is put to the user like any other.
4. **The state between holding and folding.** A gap found before the data-model doc exists
   has no marker (*to fold* was invented), and a held gap needs interim behaviour in the model
   until M0 decides it. Both want a sentence in §3(b).
5. **Work that is not code.** Timed curation runs, a user test, labelling an evaluation set:
   the run made them feature lines. §3(c) should say a milestone's features may be any work its
   exit needs.
6. **The carried-over branch line** (the stretched row above).

**Clarifications (39)**, each a sentence if wanted. The recurring ones: the class of a vendored
design reference made for the project, and of folder readmes; whether history may opt out of
the naming convention; range mentions and headings when relinking, and the path form of a
relink inside history; the gate line (or none) at the end of the reconciliation; *Needed by*
before the roadmap; how a stand-in is chosen and whether real non-personal reference data may
appear in it; a scenario clock for a time-based instance; the name of `<core>`; where the
example session sits among the docs; the stack in the primary doc or the architecture doc;
grouping and dating recovered decisions; asking the open question once, in the gate message;
the provenance note and rule rewording in the carried-over workflow; planned folders in the
layout; the glossary's areas; ADR granularity at backfill.

**Not gaps (4)**: asking the owner about renaming history (the right call); the open-questions
file in the commit after the relink commit (allowed); an owner's confirmation committed with the
next doc; amending an unpushed commit message.

## Where this leaves the kit

Seven releases on from the audit. On the same real repository, three runs in a row score
23 / 1 / 0, and no gap a release closed has come back. What the runs find now are the places
where the agent decides alone while writing — its own recommendations, edits after a gate,
work that is not code — rather than seams between the procedure and a profile. The kit is
ready for a first use on a new idea: the seam each new repository or profile finds will be
small, and the loop to close it is a release like this one.
