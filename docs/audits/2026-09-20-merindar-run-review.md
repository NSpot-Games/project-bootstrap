# Skill audit: `project-bootstrap` v2.1.0 against the Merindar run

An audit of the agent skill at `agentic-project-bootstrap` (v2.1.0) against what it actually
produced on the Merindar repository, branch `bootstrap/docs-as-contract` (commits `6ac098f` …
`1f7b90c`, 2026-09-20, roughly 17:00–17:27 in one sitting).

**Run shape.** Solo founder; repository greenfield in code but already carrying ~20 vision and
research documents; tier `full`; profile `data-driven-product` plus a `security-and-privacy`
doc borrowed from `web-app-saas`; the brainstorm step reused `docs/vision/` instead of running
fresh; the design docs were written back to back after the founder set a "finish the bootstrap"
goal.

**Citation convention in this file.** Paths into the skill repository are written **without the
`.md` extension** (`references/core/tiers §4`, `SKILL §3b`, `assets/templates/milestone`), and
the three-letter "to be decided" marker and double-brace tokens are written apart
(`{ {project} }`), so that this file does not itself trip `E001`/`E005` while it sits inside
`docs/`. That is finding **G7** in miniature.

### The one real violation, in detail

**1.10 — open questions in two places.** `references/core/lessons §1.5` names this as v1's
mistake by name ("The reference project scattered them across six docs' final sections … each
doc's section becomes a one-line pointer"). The run reproduced it exactly, and the reason is
inside the skill: `references/profiles/data-driven-product §2` prescribes "open questions" as a
*section of the outline* for four of its six design docs. The profile and the lessons file
contradict each other, and the profile is the file the skill actually reads while writing. The
cost is already visible: `docs/design/merindar-design.md` §11 opens with "Tracked in
`docs/OPEN-QUESTIONS.md` once generated; listed here so this doc is honest about what it does
not settle" — the agent noticed the tension and wrote around it.

## 2. Skill gaps exposed by this run

**G1. No docs-first path.** `references/core/adoption §3` is binary: "An empty repository — no
code, nothing to recover — is greenfield. Any repository with real code in it is brownfield."
Merindar had no code and ~20 documents including a three-round audit with taken decisions. The
run had to improvise: `SKILL §3a`'s brainstorm was replaced by reading `docs/vision/`, and every
design doc's changelog says so ("First draft from `docs/vision/v1.md` §3 and §6, the audit's
ambiguities A1–A10"). The improvisation was right, but nothing in the kit sanctions or shapes
it. A docs-first variant needs at minimum: (a) how to classify the existing folder (G3), (b)
how design docs supersede it, (c) how the brainstorm step is replaced by a reconciliation pass,
(d) what to do with contradictions between existing docs and the design docs — here handled ad
hoc by `DOCS.md` §1's "superseded by the design docs where they differ" and by
`docs/design/architecture.md`'s opening line ("Where the two differ, this one wins for phase 1
and the vision doc gets a changelog line"), both invented by the run.

**G2. `full` is a tier the linter does not know.** `references/core/tiers §1` and `§4` describe
`full` as a first-class tier and the run chose it; `AGENTS.md` says `**Tier:** full`.
`scripts/check_docs.py` `detect_tier()` returns only `standard`, `lite` or `minimal`, and every
call site tests `tier == "standard"` or `tier in ("standard", "lite")`. Setting `tier = "full"`
in `docs/.check_docs.toml` — the documented way to pin a tier — **silently disables every
milestone, plan, dependency, claim and generated-file check and turns the roadmap's sketch
sections into E005 errors**, because the roadmap is only parsed for `standard`/`lite`.
Reproduced on a copy of this repository: 23 findings, 0 milestones loaded, `generate()` returns
nothing. The run escaped only by leaving `tier` unset. Also: `minimal` is a tier the linter
invents and `references/core/tiers` never names.

**G3. Pre-existing folders that are not one of the five kinds.** `docs/vision/`,
`docs/market-research/` and `design-system/` had to be placed somewhere. The run's answers —
`DOCS.md` §2's "neither" sentence, `AGENTS.md`'s repository-layout list, the
`citation_exclude`/`exclude` keys — are reasonable and entirely invented. The kit offers no
"archive"/"history" classification, no rule for whether such a folder is linted, and no advice
on whether it should be moved (`docs/archive/`) or left in place.

**G4. Citation checking of historical documents.** Two mechanisms were needed and neither is
documented in the skill:
- `citation_exclude = ["docs/market-research"]` in `docs/.check_docs.toml`, with a hand-written
  comment explaining why. `.check_docs.toml` has **no template and no key reference anywhere in
  the kit** — `references/core/parallel-agents §1` mentions `stale_hours`, `references/core/tiers
  §2` mentions `tier`, and the remaining five keys (`citation_exclude`, `citation_roots`,
  `allow_tbd_in`, `exclude`, `codename_placeholder`) exist only in the Python source.
- Where exclusion was not available, **the history was rewritten to satisfy the linter**.
  `docs/vision/audit.md` lost its three filenames for the removed audit reviews (they became "the
  three underscore-prefixed audit files … in this folder"), the technology plan's `§1.6` became
  "§1, principle 6", and the idea doc's `§4.4` became "§4 item 4". The last two
  are `E002` false positives: `§1.6` and `§4.4` referred to *numbered list items*, which the
  linter cannot see, and the fix degraded accurate prose in a frozen historical record.

**G5. Forward citations mid-bootstrap.** Every design doc cites the ones written after it
(`docs/design/data-model.md`'s `Related:` line names `docs/design/trust-and-curation-runtime.md`
and `docs/design/architecture.md`, written two commits later). Under `SKILL §3b`'s one-doc-per-
session rule the linter is red for the whole middle of the bootstrap; running it at C10 only
(`references/core/adoption §1`) hides this, but any Stop hook installed early would block every
session. Nothing in the skill says "expect `E001` until C9" or offers a `--bootstrap` mode.

**G6. Evidence cited before it exists.** `references/core/doc-kinds §4` and
`assets/templates/milestone` both want `**Evidence of exit:**` filled at milestone creation;
`E001` resolves any `docs/evidence/<file>.md` token against the filesystem. The run's workaround is
the angle-bracket escape from `references/core/doc-kinds §3` — `docs/evidence/<m0-schema-gaps-
closed>.md` — which is that rule's *other* meaning (a name not yet fixed). The result is a
milestone whose evidence pointer looks like a placeholder forever.

**G7. The link-text pitfall.** `CITE_RE` matches any bare `<name>.md` token not preceded by
`{}<>-/.:` — so the *link text* of an ordinary markdown link is treated as a citation.
`[IDEA.md](docs/vision/IDEA.md)` yields `E001 cited file missing: IDEA.md`, and
`[v1.2.md](v1.2.md)` reports the same error **twice**. Merindar's pre-bootstrap `README.md`
(commit `main`) was built entirely from that pattern — a nine-row reading-order table linking
`IDEA.md`, `v1.md`, `v1.1.md`, `v1.2.md`, `v2.md`, `v3.md`, `technology.md`, `audit.md`. The
bootstrap deleted the table rather than fight the linter; the reading order survives only in
`docs/vision/README.md`. That is a linter bug driving a content decision.

**G8. Every feature needs a plan file on day one.** A milestone feature line cites its plan
path in backticks, so `E001` fires until the file exists. The run therefore wrote **twelve stub
plans** (`docs/plans/M0/M0-02-…` through `docs/plans/M1/M1-07-…`), each status `grounding`, each
with the same manufactured Objective ("… Grounding not yet done; the first session on this
feature fills Current state, Approach and Tasks per `docs/WORKFLOW.md` §2") and the same
placeholder task `T1 — Ground the feature and write the tasks`. Nothing in
`references/core/lifecycle` or `assets/templates/milestone` says whether a feature line may
point at a plan that does not exist yet; the linter decided the policy by accident.

**G9. One doc per session versus one sitting.** `SKILL §3b` states the rule and its reason
("a one-shot bootstrap that writes several docs back to back produces shallow docs — each later
one gets less scrutiny than the last") and `SKILL §7` allows "unless the user explicitly says
to" — with no procedure for what to do then. The run took the exception and the prediction
partly came true: `docs/design/curation-tooling.md` (61 lines) and
`docs/design/security-and-privacy.md` (86 lines) are visibly thinner than
`docs/design/data-model.md` (364) and `docs/design/trust-and-curation-runtime.md` (176), and
both were in the four-doc commit `0bf77b1`. A compressed mode needs its own shape: batch review
gate, an explicit "these two are thin, revisit at phase review" note, or an ordering that puts
the thin ones first.

**G10. Profile doc lists are closed, and projects are not.** The profile table is the skill's
only instruction for which design docs to write. Merindar publishes personal data about natural
persons before consent under GDPR legitimate interest — a legal centre of gravity that
`references/profiles/data-driven-product` does not model at all (its architecture doc gets one
word, "security"). The run borrowed `docs/design/security-and-privacy.md` from
`references/profiles/web-app-saas §2` and recorded the borrowing in `AGENTS.md` ("Profile:
data-driven-product (plus the security-and-privacy doc)"). `references/profiles/README §1` only
says to pick one profile and revisit at the next phase; there is no sanctioned "add a doc from
another profile" move and no place to record it.

**G11. `docs/CURRENT.md` is empty at bootstrap.** `SKILL §5` says "Open `docs/CURRENT.md` and
claim `M0-01`". `assets/templates/milestone` ships `**Status:** planned`, and
`gen_current()` builds "Next unclaimed features" only from milestones whose status is `in
progress`. So the first generated `docs/CURRENT.md` names a phase and nothing else. The run
discovered this the hard way — commit `1f7b90c`, "M0-01: mark M0 in progress so CURRENT.md lists
the unclaimed features" — a fix invented by the agent, not instructed.

**G12. Token substitution is a manual chore with no check.** `SKILL §4.3` says substitute every
double-brace token from `assets/templates/README`'s table; `E005` only catches leftovers. Six
process files were retyped by hand. Two values in the table have no obvious source for a
docs-first run (`{ {commands} }` — the project has no build yet; the run wrote "Until M1 lands,
these do not exist"), and there is no scripted substitution step.

**G13. Line endings and repository hygiene.** The kit carries its own `.gitattributes`
(`* text=auto eol=lf`, `*.sh text eol=lf`) and ships neither it nor a `.gitignore` to the
project. Merindar has neither file; Git's `core.autocrlf=true` is active, so 17 of the
bootstrap's files are CRLF in the working tree, including `tools/hooks/stop.sh` (verified:
`#!/bin/sh\r\n`) — a shell script that will fail on a POSIX host if it ever reaches one with
CRLF intact — and `git status` now shows an untracked `tools/__pycache__/` created by running
the linter.

**G14. No guidance for the bootstrap's own branch and PR.** `SKILL` never mentions a branch, a
commit or a PR; `references/core/parallel-agents §5` covers only feature branches
(`feat/M<n>-<nn>-<slug>`). The run invented `bootstrap/docs-as-contract`, committed in seven
steps, and had to add a transitional rule in two places (`AGENTS.md` "Conventions",
`docs/WORKFLOW.md` §4) about branching from the bootstrap branch until PR #1 merges. That rule
will be stale the day the PR merges and nothing schedules its removal.

**G15. Two Stop hooks.** `SKILL §4.2` copies `scripts/hooks/stop.sh` to
`<project>/tools/hooks/stop.sh` "if the user wants the linter to run without being remembered",
and `scripts/hooks/README` notes that with the plugin installed "installing both is harmless;
the linter runs twice". The run copied the file and never wired it — there is no `.claude/`
directory in Merindar — so `tools/hooks/stop.sh` is dead weight that `AGENTS.md` nonetheless
advertises ("`tools/hooks/stop.sh` — the Stop hook"). The skill should ask, not copy by
default.

**G16. `assets/templates/PROJECT-README` is four lines.** Merindar already had a good README
(a paragraph, a nine-row reading table, a related-projects section). The template offers
`{ {Project} }`, `{ {three_sentences} }` and two pointer lines, with no rule for merging with an
existing one. The run produced a decent hybrid (one long paragraph, a six-row "Where things
are" table, the geo-engine link) but lost the per-version reading order; a template with a
"Where things are" table and a "keep whatever the existing README had that agents do not
duplicate" instruction would have avoided the loss.

## 3. Quality of the output

**Design docs: strong, and not boilerplate.** `docs/design/data-model.md` (364 lines, 17
entities, derivations, validation rules, ID rules) and
`docs/design/trust-and-curation-runtime.md` (state machines, SLA table, ranking rule) are
genuinely buildable. `docs/design/example-casa-din-vale.md` is the best artefact in the run and
vindicates the profile's highest-value step: five real fixture files, a walkthrough that names
actual field values (`rank_key` 2020735, `tier_at_time = t2`, `channel = whatsapp`), **fifteen
numbered schema gaps each phrased as a concrete field addition**, and a cross-reference check
that found two missing fixture directories. That is a next-session-ready work queue, not prose.

**Thin spots.** `docs/design/curation-tooling.md` §4 ("Who uses each tool and how often") is a
single paragraph of estimates; `docs/design/security-and-privacy.md` is 86 lines for a domain
that `docs/OPEN-QUESTIONS.md` says needs a lawyer. Both were in the four-doc commit. The
headings in `docs/design/merindar-design.md` carry the profile's game vocabulary ("player") into
a travel product and have now frozen it as an anchor (1.15).

**Roadmap: good shape, honest wave.** Ten milestones in P1 with only the first two written out;
sketch goals are one sentence but dense and specific ("the `SearchEngine` interface with the
Postgres implementation, the document builder, facets…"), which is more useful than the
template's one-liner and still cheap to revise. P1's exit restates the measurable gate from
`docs/design/merindar-design.md` §12 rather than inventing a new one — correct.

**Plans: one excellent, twelve inert.** `docs/plans/M0/M0-01-apply-schema-gaps.md` is a model
plan: a Current state with five grounded bullets naming all fifteen gaps, two rejected
alternatives, two named risks with their checks, a docs-to-update list, and four tasks each with
a real verification command. The other twelve add nothing a reader could not get from the
milestone file, and they cost: `docs/plans/README.md` lists twelve `grounding` plans as "active"
work, which is the index's most prominent section. They are not harmful, but they are noise, and
their identical boilerplate Objective lines risk being mistaken for grounding that happened.

**`docs/CURRENT.md`: adequate only after the manual fix.** As now generated (17 lines) it gives
a new session the phase, the in-progress milestone, the one claimed feature with its plan path
and stamp, and five unclaimed features by ID and title. That is the right content. What it does
**not** give — and a new session would want — is the current milestone's exit criteria in one
line, and any pointer to `docs/OPEN-QUESTIONS.md` rows that block the named features (four of
the 14 rows block `M0`/`M1` work).

**Glossary: derivable and derived.** ~60 terms, six areas, nearly every entry ending in a
section citation or a table/column name (`places.tier_method_note`, `contact_events`,
`trail_hosts`). Bilingual pairs (*Place (loc)*, *Host (gazdă)*) are the right call for a
Romanian product. Its "words we avoid" list is the strongest part and is already doing work.
Its one weakness is the conflict with the frozen "player" headings (1.15).

## 4. Linter findings

### Bugs

- **B1 — unknown tier silently disables everything.** `detect_tier()` returns `cfg.tier`
  verbatim when it is not `auto`; every check and every generator then no-ops. With
  `tier = "full"` — the tier this project declares — you get 0 milestones loaded, no generated
  files, and `E005` on every roadmap sketch section because the roadmap is never parsed. There
  is no validation of the `tier` key and no `E012` for an unknown value. Severity: high; this is
  a silent green-to-nothing failure.
- **B2 — link text is parsed as a citation.** `[IDEA.md](docs/vision/IDEA.md)` → `E001 cited
  file missing: IDEA.md`. `[v1.2.md](v1.2.md)` → the same `E001` twice. The fix is to strip or
  skip the `[...]` span of a markdown link before matching.
- **B3 — `E002` on numbered list items.** A citation such as the technology plan's `§1.6` resolves the file, then fails the
  anchor because `numbered_headings()` only reads headings. Any project whose prose cites a
  numbered item inside a section gets a false error, and the pressure is to edit the prose.
- **B4 — `check_generated` under-reports.** `E003` only inspects rows starting `| M`, so a
  wrong *title* column produces only `W003`; a missing `docs/plans/README.md` produces only
  `W003` while a missing milestones index produces `E003`. Inconsistent severity for the same
  class of drift.
- **B5 — CRLF asymmetry.** `read_text()` normalises CRLF for reading, and `--fix` writes with
  `newline="\n"`, so the four generated files are permanently LF while everything else follows
  the platform. On a Windows checkout with `core.autocrlf=true` this guarantees a mixed-ending
  repository (17 files here) with no `.gitattributes` to settle it, and the copied
  `tools/hooks/stop.sh` ends up CRLF.

### Missing checks

- **M1 — no status-vocabulary check.** `**Status:** wip` on a milestone, `started` on a plan,
  `running` on a phase, `wibble` on a design doc: verified, all pass with zero findings. Worse,
  an out-of-vocabulary milestone status *disables* `E009` (no exit criteria) and `E007`
  (done-with-unticked-features) for that milestone, and an out-of-vocabulary plan status hides
  it from `W001` and from `docs/CURRENT.md`. A typo silently removes a file from enforcement.
  Proposed `E013`.
- **M2 — no design-doc structure check.** No check that a file in `docs/design/` opens with the
  header from `assets/templates/design-header`, that its `**Status:**` is one of
  `draft|stable|living`, or that it ends with `## Changelog`. `references/core/doc-kinds §3`
  states all three as rules. Verified: a `docs/design/` file with neither header nor changelog
  produces zero findings. Proposed `E014` (header/status) and `E015` (changelog).
- **M3 — milestone size 3–10 unenforced.** `references/core/layers §5` is a hard rule; a
  milestone with 15 features lints clean (verified). Proposed `W004`.
- **M4 — no length checks.** `AGENTS.md` under 120 lines and `docs/CURRENT.md` under 40 are
  stated in `references/core/lessons §1.17` and `references/core/long-horizon §7`; only the
  generator's own construction bounds the second, and nothing bounds the first.
- **M5 — phases are parsed but never checked.** `P<n>` status vocabulary, "exactly one phase
  `active`", "an `active` phase has an exit criterion", "a `done` phase has all its milestones
  `done`" — none are checked. Phases are a `full`-tier feature (B1) and Merindar has five of
  them; the linter's only use of a phase is the `**Phase:**` line in `docs/CURRENT.md` and the
  sketch range for `E005`.
- **M6 — feature line and plan file can disagree.** The path in a feature line is only checked
  for existence; nothing verifies that the plan at that path has a matching ID, or that the
  plan's `**Milestone:**` matches the directory it sits in.
- **M7 — no `--bootstrap`/`--new` mode.** Nothing lets the linter distinguish "this citation
  target has not been written yet" from "this citation is broken" (G5, G6, G8).

### Confirmed non-issues

- Sketch detection when a phase carries the status and its milestones do not **works**:
  `parse_roadmap()` records the phase's range with `section_end()`, which spans nested headings,
  so `M10`…`M17` under sketch phases may carry the unresolved marker. `M2`…`M9` under the active
  `P1` each carry their own `**Status:** sketch` — the run got this right.
- The angle-bracket escape genuinely suppresses `E001` (`docs/evidence/<name>.md`), because the
  lookbehind rejects a token preceded by `<`.
- `W001` did not false-positive on the fresh claim (stamp `2026-09-20T14:23Z`, correctly UTC for
  a 17:23+03:00 commit).

### Tests

`tests/test_check_docs.py` (63 tests) is thorough on what exists and has no test for any of
B1–B5 or M1–M7. `tests/fixture/valid/` is a `standard`-tier project only: there is no `full`
fixture, no design-doc fixture with a changelog, and no fixture exercising phases beyond one.
`tests/test_skill_package.py` verifies the skill package and both Stop hooks well, but nothing
checks that `references/core/tiers`' tier names match `detect_tier()`'s — the check that would
have caught B1.

## 5. Improvement proposals, ranked

**P1 — Make `full` a real tier. (L)**
*Change:* `detect_tier()` returns `full` when `docs/roadmap.md` contains `P<n>` headings or the
