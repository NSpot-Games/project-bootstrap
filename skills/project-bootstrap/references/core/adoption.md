# Adoption

Two procedures get a project onto this kit: greenfield, for a project that doesn't exist yet, and brownfield, for one that already has code. Both end at the same place — a project with the tier-appropriate files in place, the linter passing, and a first session ready to open — but greenfield gets there by writing, and brownfield by recovering what the code and its history already know.

## 1. Greenfield

Each step below is a conversation with an agent (or with yourself) that ends in a file. Do not skip ahead to code — a milestone written before the design doc it depends on is a milestone against an imagined project.

**C0. Decide five things before writing anything.** The project's name and codename; the file naming convention (kebab-case, unnumbered, with the reading order stated in `<project>/DOCS.md` — numbered prefixes look tidy and then break every cross-reference the first time something is reordered); where the example instance will live (`<project>/cases/<id>/`, `<project>/fixtures/`, or similar — the architecture doc will cite it); the tier (`references/core/tiers.md §1`); and the profile (`references/profiles/README.md`). Changing the name or the naming convention later touches every file; deciding tier and profile now means every later step knows which design docs it is writing.

**C1. Brainstorm the project.** A conversation, no file yet: what it is, who it's for, what's hard, what the real alternatives are, what will not be built. Push on the hardest technical constraint early — it usually shapes the architecture more than anything decided on purpose. Write down only a list of decisions made and questions left open.

**C2 through C7. Write the profile's design docs, phase 1 only.** `references/profiles/<name>.md` names exactly which design docs the chosen profile calls for and gives each one's section outline; write them in the order that profile gives, one conversation per doc, covering phase 1 only (`references/core/long-horizon.md §3`) — later phases get their own design docs when they become `active`. Wherever the profile places its example instance — canonically C4 — write a complete, real instance of the project's central data or artifact, in the actual schema, before finishing whichever docs depend on it. This is the single highest-value step in the whole procedure: it exposes every field the schema is missing, every ambiguity a prose description hid, and every place a design doc hand-waved, in one sitting, in a way reasoning about the schema in the abstract never does.

**C8. Write the roadmap.** Milestones in order, each with a goal and, for phase 1's milestones, a measurable exit. Apply the rolling wave here (`references/core/long-horizon.md §1`): the current and next milestone are written out `planned`, with real exits and milestone files; everything beyond is `sketch` — a goal sentence in the roadmap and nothing more, until a phase review promotes it.

**C9. Generate process files from `assets/templates/`.** `<project>/AGENTS.md`, `<project>/CLAUDE.md`, `<project>/DOCS.md`, `<project>/docs/WORKFLOW.md`, `<project>/docs/GLOSSARY.md`, `<project>/docs/OPEN-QUESTIONS.md`, `<project>/docs/decisions/AGENTS.md`, `<project>/README.md`, and the milestone and plan files the rolling wave's current and next milestones need. Every `{{token}}` in a template is filled from what C0–C8 already decided — `{{project}}` and `{{Project}}` from the name, `{{profile}}` and `{{tier}}` from C0, `{{product}}` from the profile's primary design doc, and so on; the full list of tokens is `assets/templates/README.md`. A template copied into the project has no `{{` left in it once filled; the linter's `E005` check catches any that remain.

**C10. Run the linter.** `python tools/check_docs.py --root . --fix` — this checks the fresh project (every citation resolves, no leftover placeholders) and generates the four indexes (`references/core/parallel-agents.md §2`) for the first time. Fix whatever it reports before the first agent session opens.

**C11. Open the first session.** Open the current milestone's first feature and follow `<project>/docs/WORKFLOW.md`. This feature is nearly always "fold the schema gaps the example instance surfaced back into the data model" — C4's highest-value step almost always leaves gaps behind, and closing them first means the rest of the project builds on a schema that has already met reality once.

## 2. Brownfield

Brownfield replaces the writing steps with recovery steps: the code and its history already encode most of the decisions greenfield would otherwise start from scratch.

**1. Inventory.** Read the repository tree, the build and test commands (`package.json`, `Makefile`, `pyproject.toml`, or whatever the stack uses), any existing docs (a `README`, a wiki export, comments at the top of key files), the open issues in whatever tracker the project uses, and the recent commit history (`git log --oneline -50` or similar) to see what's actively moving. Nothing gets written yet; this pass tells the later steps where to look, and its findings become the "gaps found" that the first session closes (`§2`, step 7).

**2. Reverse-engineer the architecture doc from the code.** Walk the source tree module by module and write `<project>/docs/design/architecture.md` with header status `draft` (`references/core/doc-kinds.md §3`) and a "confidence" column alongside each module — high where tests and naming make the intent clear, low where the only evidence is the code's behaviour and a guess. It is marked `draft` because it was reverse-engineered from code and not yet confirmed by the people who built it; per `references/core/doc-kinds.md §3` it may still change on first contact, and the per-module confidence column says where that is most likely.

**3. Recover the data model from schemas, migrations, or types.** Find the schema wherever it actually lives — `*.sql` migrations, an ORM's model classes, a `prisma/schema.prisma`, hand-written types — and write it up as the profile's data-model doc (`references/profiles/<name>.md`). Then pull one real record from the running system or a fixture, anonymise anything personal, and write it up as the example instance doc; a model recovered from types alone still needs a real instance to expose what the types didn't capture.

**4. Backfill ADRs from git history and existing docs.** Search the commit history and any existing design notes for hard-to-reverse choices already made — a framework switch, a storage choice, an API shape locked in by clients. Search terms like `git log --all --grep="switch\|migrat\|decid\|instead of"` find some of them; reading the oldest design notes finds the rest. Each one becomes `<project>/docs/decisions/<NNNN>-decision-as-a-sentence.md` (`assets/templates/adr.md`) with `**Status:** accepted` and `**Date:** recovered` — accepted immediately, since the choice was already made and lived with, not proposed for a human to weigh now.

**5. Write the design doc as a vision-and-current-state document.** Not "what we plan to build" but "what this is now and where it's headed" — the profile's primary design doc (`references/profiles/<name>.md`), grounded in steps 2–4 rather than imagined. Non-goals come from what the team has already declined, not from a fresh brainstorm: closed issues marked won't-fix, features requested and rejected, paths the architecture doc's confidence column flagged as deliberately avoided.

**6. Build the roadmap from the issue tracker.** Whatever is actively being worked becomes `<project>/docs/milestones/M1.md`, status `in progress`; the rest of the backlog becomes `sketch` milestones, grouped into phases in `<project>/docs/roadmap.md` the same way a greenfield roadmap would be (`references/core/long-horizon.md §1`). Issues stay in the tracker rather than being copied wholesale into the kit's files: a milestone or feature line cites the issue as `(tracker: #123)`, and the milestone file is authoritative for status — if the tracker and the milestone file disagree about whether something is done, the milestone file is right, because the tracker is not what the linter checks or what a session reads at Ground.

**7. Generate, lint, and open.** Generate the process files from `assets/templates/` as in greenfield's C9, filling tokens from what steps 1–6 recovered rather than from a fresh conversation. Run `python tools/check_docs.py --root . --fix`. Open the first session on a feature literally named "close the gaps the inventory found" (step 1) — recovered docs are drafts by construction, and the first session's job is to firm up whichever ones the rest of the team will touch first.

## 3. Which procedure

An empty repository — no code, nothing to recover — is greenfield. Any repository with real code in it is brownfield, even if that code is rough or partial: there is more signal in the code than in re-deciding everything from a blank brainstorm. A repository with code but no docs is still brownfield, and in practice spends most of its effort in steps 2 through 4 (`§2`) — the architecture, the data model, and the ADR backfill — since there is nothing already written down to shortcut those.

A repository with no code but with documents already in it — vision notes, research, a spec, a journal — is neither: greenfield's blank brainstorm would throw the thinking away, and brownfield's recovery steps have no code to recover from. That is docs-first (`§4`): the existing documents are the brainstorm's input, and the first job is to say which of them are contract, which are history, and where they disagree.

## 4. Docs-first

Docs-first replaces the brainstorm (C1) with a reconciliation pass and adds a classification step before it; everything from C2 on is greenfield's.

**1. Inventory and classify.** Read every existing document and classify each file or folder as one of three: *contract* — it describes what will be built and becomes, or feeds, one of the profile's design docs; *history* — a dated record of thinking (a vision note, a journal, a research write-up), kept as written, never edited, cited as history; *external reference* — material from outside the project (a standard, a vendor doc, a paper). Hold the classification in the scratch list; at generation it is written into `<project>/DOCS.md §1`, one line per file, with the design doc that supersedes each contract-or-history file.

**2. Rename and relink first.** If any file will be renamed or moved to fit the naming convention decided in C0, do every rename and fix every inbound link in one commit before any design doc is written. A design doc that cites a path which then moves is a broken citation on day one.

**3. Reconcile.** Instead of brainstorming from blank, read the history for three things and write them into the scratch list: the decisions already taken, each with its date and the file that records it; the questions the history leaves open; and every contradiction between documents — two notes that disagree about the same thing. Each contradiction is a decision the user has to make before the design doc that depends on it is written, so put the contradictions to the user first, starting with the one that shapes the architecture most, exactly as C1 pushes on the hardest technical constraint first. Decisions already taken become ADRs at generation (`§2`, step 4, the same backfill brownfield does), dated as they were decided.

**4. Derive the design docs.** Write the profile's docs as C2 through C7 describe, one per session, each derived from the history with citations back to the notes it came from. Each design doc's first paragraph states what it supersedes ("supersedes `<project>/docs/vision/<file>.md` for <topic>"); from then on the design doc is the contract and the note is the record of how it was reached. History is never edited to agree with the design doc; where they differ, the difference is a decision, recorded in the design doc's changelog and, if hard to reverse, an ADR.

**5. Keep the linter off frozen prose.** Add the history folders to `citation_exclude` in `<project>/docs/.check_docs.toml` at generation. A dated note may cite a section that has since been renumbered or a file that has since moved; the note is right for its date, and the linter must not pressure anyone into rewriting it.
